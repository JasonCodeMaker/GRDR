Hypothesis

H1: The loss-side fix is necessary; the cheap data-side fix (P1 shared token_idx) would structurally degenerate to NLT=1-equivalent training (3 dormant MLPs) — supported by diagnostic §2.5 truth-table row 3 + archived MSR-VTT E2.4F.1 cross-dataset evidence. (No F3 cell — see P1 reference doc for the argument.) H2 (primary gate): P3 + view-diversification bundle (soft-weighted CE via token_idx + inter-slot orthogonality regularizer + per-slot k-means init at step 0 only; SHARED 4096 codebook) is sufficient for NLT=4 multi-view to beat NLT=1 baseline at 500K scale. H3 (K1 stacked-fix gate): explicit per-slot k-means seed at every loop boundary (--codebook_seed_all_slots: dedup-by-video + return_all=True; faiss-GPU k-means on [num_videos × N, D] instead of select(token_idx)-reduced [num_text_samples, D]) outperforms F2 alone at 500K because consequence B of select(token_idx) carries non-trivial signal loss that F2's train-step fixes do not recover; tested by K1 vs F2. H2-scale: the winning recipe (F2 alone if H3 fails; F2 + K1 if H3 holds) at full 2.15M beats production anchor (CanHit@100 = 95.57) — tested by V.

Seed plan

Single seed s42 for every cell — including V. The 500K cells (B1/B2/B3/F2) establish the apples-to-apples NLT=4 vs NLT=1 comparison; V then takes the F2 winning recipe and trains a single full-chain seed at 2.15M scale on Bunya H100 to directly attempt the production anchor (CanHit@100 = 95.57). Multi-seed validation is deferred to a follow-up package — this sprint optimizes for "does the recipe scale up?" rather than "is the recipe stable across seeds?". If V wins, the next package runs 2 more seeds at 2.15M to satisfy the CLAUDE.md "Current Best" multi-seed requirement; if V loses, the recipe stays as a 500K-only result and 2.15M scale-up is reconsidered.

Run conventions (global rules, package-wide)

Binding on every experiment in this package (P0, B1, B2, B3, F2, K1, S, V) and any follow-up cell added later:

  1. R-LOG: wandb required. Every training and evaluation run must log key metrics to wandb (loss curves, CE/RQ/recon losses, codebook-usage diagnostics, eval CanHit@K, avg_candidates_per_query, throughput). No silent file-only runs. Launcher scripts must pass --use_wandb (or equivalent project flag) and set --wandb_project / --wandb_run_name to 2026-05-24-multiview-fix-pipeline / <cell-id>_s<seed>. A run that crashes before its first wandb step counts as a failed launch and must be re-launched, not patched post-hoc.
  2. R-BUNYA-24H: interactive 24h allocation for on-node debugging. Every Bunya cell (compute: "bunya" in inventory — currently F2, V; plus any future Bunya cell) must run inside an interactive salloc allocation of --time=24:00:00 (gpu_sxm partition, qos=sxm). No sbatch for these cells during the workstation→Bunya transfer window. Rationale: the multi-view pipeline edits (all-slot CE, view-diversification bundle) are first-time-on-Bunya code paths; live shell access on the compute node is required for fast iteration on shape/dtype/oom issues without burning a fresh queue wait per fix. Parallel cells share a single 2-GPU allocation via CUDA_VISIBLE_DEVICES=0/1 when SXM availability allows (see MEMORY: Bunya H100 SXM interactive pattern, Pre-allocate Bunya GPU before need).

enforcement: launcher scripts under scripts/ must hard-code both rules (no opt-out flag). Tracker launch-readiness (T21) ack must confirm both rules satisfied before any cell flips to EXPERIMENT_RUNNING. A cell that ran without wandb or on a non-interactive Bunya batch job is not a valid result-gate witness — re-run is required before the row can be inserted into results.html.
